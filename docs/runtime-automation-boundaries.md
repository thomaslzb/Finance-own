### 1.5 锁屏状态下的窗口级渲染

这一结构解释了为什么仅依赖 `Process.MainWindowHandle` 或标准按钮句柄无法稳定控制主界面。

## 3. 当前失败的最可能原因

从现有日志和环境判断，至少存在三个限制：

### 3.1 位数不匹配影响 GUI 包装层

当前环境：

- Python：`64-bit`
- 目标程序：`32-bit`

这会让部分 GUI 自动化包装层能力变差或不完整，但不影响当前已完成的运行时 DFM 只读提取。

### 3.2 权限级别不足

运行时已出现工具警告：

- 当前 Python 进程没有足够权限稳定修改目标 GUI

这意味着：

- 只读枚举可行
- 写入式交互、点击式交互不稳定

### 3.3 自绘/混合 UI

当前主程序中已看到：

- `TRz*` 自绘控件
- `TNodeForm / TNodeWrapForm`
- `TWkeWebbrowser / wkeWebWindow`

这说明：

- 程序并不只是标准 Win32 控件拼装
- 某些按钮和页签可能不会响应标准消息级点击方式

## 4. 当前最有价值的结论

截至 2026-07-28，当前最稳妥的自动化定位是：

- `适合`
  - 运行态结构确认
  - 组件清单梳理
  - 可见/隐藏页签识别
  - 已加载窗体识别
  - 全量运行时 DFM、字段和事件提取
- `不适合`
  - 直接把消息级点击当成可复用切页方案
  - 依赖当前环境做稳定页面跳转

## 5. 后续最可行路线

如果后续还要继续补视觉和交互证据，技术优先级建议如下：

1. 先确保原管理员实例正常退出且账本已保存
2. 以 `RunAsInvoker` 启动工作区副本，避免单实例互斥和 UIPI 隔离
3. 优先修复 Computer Use 对 32 位 Delphi/Rz 自绘窗口的枚举能力，或提供受支持的同完整性级别桌面代理
4. 确认桌面会话已解锁后，再使用图像级输入补拍页面和验证跳转
5. 只有普通权限实例仍无法操作时，再准备管理员级自动化环境

当前 Computer Use 插件可控制其它普通窗口，但无法发现普通权限 MoneyHome8 的可见 Delphi 主窗口；这与 Win32 枚举结果不一致，问题更可能位于插件的窗口发现兼容性，而不是进程没有启动。
