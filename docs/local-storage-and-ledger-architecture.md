# 本地存储与总账架构决定

本文固定 Finance Own 的本地数据库、交易真相、专属业务扩展和后续双重记账迁移方向。功能兼容以 MoneyHome8 的真实页面和测试账簿证据为准，内部表结构不复制旧 Jet 数据库。

## 1. 决定摘要

1. 主账簿继续使用 SQLite，作为无需数据库服务的本地应用文件格式。
2. SQLite 文件固定 `application_id=1179604814`（ASCII `FOWN`）和 `user_version`，打开时同时校验版本、文件身份、快速完整性和外键。
3. 金额使用整数最小货币单位；数量、价格和汇率使用整数值加显式 scale，不使用浮点数保存财务真相。
4. 当前兼容阶段保留 `transactions + transaction_entries` 的方向分录投影，工资、保险、债务和投资等复杂业务使用类型化扩展表保存通用分录无法表达的事实。
5. 最终总账目标是每笔已过账交易由至少两条 posting/split 构成，并按计价币种或明确的换算金额保持借贷平衡。分类将成为可记账的分类账户或由稳定系统账户承接对方分录。
6. 双重记账升级必须分阶段完成，不能直接改写现有核心表并同时破坏报表、投资、保险、导入和旧库迁移适配器。

## 2. 官方系统证据

| 系统 | 官方设计事实 | Finance Own 采用方式 |
| --- | --- | --- |
| [SQLite application file format](https://www.sqlite.org/appfileformat.html) | SQLite 可作为应用文件格式；应用可使用文件头字段识别自己的数据库 | 固定 `application_id`，拒绝误打开其它 SQLite 文件 |
| [SQLite STRICT tables](https://www.sqlite.org/stricttables.html) | `STRICT` 表执行更严格的类型约束，完整性检查也验证列类型 | 继续使用 `STRICT`、外键、CHECK、唯一约束和触发器 |
| [SQLite WAL](https://www.sqlite.org/wal.html) | WAL 提升读写并发，但会产生 `-wal`、`-shm` 辅助文件，并要求检查点与正确备份 | 当前保持回滚日志的单文件操作语义；出现真实并发需求后再启用受控 WAL |
| [GnuCash transactions](https://www.gnucash.org/docs/v5/C/gnucash-guide/chapter_txns.html) | 一笔交易至少在两个账户之间交换价值，每个部分是 split，可扩展为多分录交易 | 最终总账采用平衡 posting/split；工资、转账、手续费和投资事件均是一笔复合交易 |
| [Actual Budget split transactions](https://actualbudget.org/docs/transactions/split-transactions) | 拆分子项总额必须等于父交易金额 | 分类拆分和工资组成必须有可重复的金额守恒校验 |
| [Actual Budget transfers](https://actualbudget.org/docs/transactions/transfers) | 转账在两个账户中形成关联记录 | 转账两侧必须由同一业务标识和同一数据库事务提交 |
| [Actual Budget sync](https://actualbudget.org/docs/getting-started/sync) | 本地文件与同步状态需要独立处理，冲突不能静默覆盖 | 本地账簿始终独立可写，同步批次、冲突和墓碑与核心真相分离 |

Firefly III 官方文档站在本次环境中返回 Cloudflare 验证页；其复式记账、周期交易、规则、目标储蓄、多币种、报表和 REST API 能力改由官方仓库 README 与官方文档源码确认。该证据用于模块边界参考，不改变首版本地 SQLite 桌面应用定位。

## 3. 当前可执行模型

### 3.1 通用交易

- `transactions` 保存业务身份、账簿内序号、日期、类型、状态和说明。
- `transaction_entries` 保存账户、方向、金额、币种、角色和可选分类。
- 已过账余额只从账户分录投影，账户表不保存可漂移余额。
- 交易头、全部分录、标签、附件和专属扩展必须在一个 SQLite 事务中提交。

当前模型可以稳定表达收支、转账、手续费、账户拆分和余额投影，但收入或支出允许只有一条账户分录，因此不能宣称已经实现会计意义上的完整双重记账。

### 3.2 类型化扩展

专属表只保存通用交易不能表达的业务事实，不能复制账户余额：

- 工资：收入组成、普通扣款、个人缴费、公司缴费、人员和社保账户。
- 保险：保单条款、资金事件、现金价值快照与变更历史。
- 债务和信用：本金、利率、期限、账单及还款条款。
- 投资：标的、成交、持仓批次分配、行情和合同参数。

第七版迁移新增工资扩展后，`v_payroll_income_reconciliation` 同时核对：

```text
实收现金 = 收入合计 - 普通扣款 - 个人社保缴费
社保权益增加 = 个人社保缴费 + 公司社保缴费
```

工资提交服务必须确认业务公式、实收账户分录和社保账户分录全部匹配，才允许完成已过账状态。

## 4. 双重记账目标模型

后续核心迁移采用以下稳定概念：

- `journal_transactions`：业务交易头、状态、修订号和稳定业务标识。
- `ledger_accounts`：资产、负债、权益、收入、费用及系统过渡账户。
- `postings`：每条借贷分录，包含账户、币种、原币金额和本币折算金额。
- `posting_links`：连接工资组成、投资成交、保险事件等专属事实与具体 posting。

每笔已过账交易至少满足：

1. 至少两条 posting。
2. 同一平衡币种下借方合计等于贷方合计。
3. 跨币种交易保存明确汇率快照、舍入差额和必要的汇兑损益或舍入账户。
4. 作废使用反向分录或保留原交易的 void 状态，不物理删除财务历史。
5. 修改已过账交易生成新修订或替代交易，保留原始版本、操作者来源和时间。

MoneyHome8 的用户界面仍可显示“流入/流出、分类、转账、工资”等熟悉概念，这些字段由 posting 投影生成，不要求用户直接输入借方和贷方。

## 5. 分阶段迁移

### 阶段 A：兼容骨架

- 保留现有方向分录和查询视图。
- 完成各页面的真实行为、金额公式和生命周期校准。
- 使用类型化扩展表补齐复合业务事实。
- 所有新账簿写入应用标识，并使用 `synchronous=FULL`。
- 只对具有 v6 核心表指纹或合法 Finance Own `application_id` 的 v7/v8 账簿执行到 v9 的原子升级；其它版本或错误文件身份必须拒绝打开。

### 阶段 B：平衡总账并行写入

- 新增总账账户和 posting 表，不立即删除旧表。
- 每个已校准写入服务同时生成兼容分录和新 posting。
- 自动比较两套余额、报表和业务扩展关联，差异为零后才推进。

### 阶段 C：读取切换

- 余额、流水和报表改从平衡 posting 读取。
- 旧方向分录变为迁移兼容视图或只读历史表。
- 旧库导入先转换为规范业务命令，再生成平衡 posting，不把 Jet 字段直接映射为最终表结构。

## 6. 文件、并发与备份

- 当前使用 SQLite 回滚日志，保持用户对单一账簿文件的直观认知。
- `synchronous=FULL` 优先保护财务写入的断电持久性，后续只能依据真实性能基准调整。
- 不允许在账簿打开且正在写入时只复制主数据库文件作为可靠备份。
- 备份应使用 SQLite Backup API 或 `VACUUM INTO` 生成一致快照，再计算哈希并写入账簿外备份清单。
- 如果后续启用 WAL，必须使用受控检查点和备份流程处理 `-wal`、`-shm`，不能把活动主文件单独视为完整账簿。

## 7. 当前验证边界

- 第七版工资迁移、第八版人员资料迁移、第九版人员列表生命周期迁移、第十版待摊费用迁移、第十一版存款利率版本迁移、第十二版财务目标进度基线迁移和第十三版计划/提醒实例迁移，以及文件标识、工资公式、工资账户投影、待摊期次金额、利率批次完整发布、负值目标基线、计划执行/跳过约束、提醒处理约束和 v6/v7/v8/v9/v10/v11/v12 升级已有自动化验证。
- 当前方向分录尚未具备数据库级全局借贷平衡约束。
- 工资中公司缴费的目标投影已经固定，但 MoneyHome8 的精确社保报表口径仍需真实提交样例校准。
- 跨币种平衡、投资成本法、作废修订和旧库完整迁移仍不能标记为已兼容。
