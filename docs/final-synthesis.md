# MoneyHome8 重构综合结论

本文档是当前阶段的总综合结论，目标是用一份短文档回答：

1. 我们已经确定了什么
2. 还没有确定什么
3. Rust 重构现在最稳妥的路线是什么

## 1. 已经确定的核心事实

### 1.1 产品不是“小记账工具”

当前证据已经明确，`财智8` 至少覆盖以下能力：

- 账本生命周期
- 账户体系
- 通用收支/转账/流水
- 债权债务/信用卡/应收应付
- 外汇、证券、基金、债券、期货、黄金、贵金属、融资融券
- 保险、社保、重大资产
- 预算、提醒、财务规划、财务目标
- 导入导出
- 同步、通知、行情
- 报表与分析中心

### 1.2 至少存在四个顶层工作区

当前已确认：

- `财务数据`
- `财务报表`
- `财务分析`
- `记账`

其中前三个已经拿到真实页面证据；`记账` 仍缺页面级截图，但公共录入、转账、分拆、模板、计划和流水操作已由运行时 DFM 直接确认。

### 1.3 它不是单一数据库系统

当前最稳的多数据源结构是：

1. `test.mh8`
   - 用户主账本
2. `mhlink.mdb`
   - 共享参考库
3. `MoneyHome8.data`
   - 可解压的受控 Jet 内置库
4. `MoneyHome8.cache`
   - 综合检索缓存
5. `Investment.cache`
   - 投资品分类缓存
6. `mh.mdw`
   - 工作组权限文件
7. `user.cfg` / `UseInformation.cfg`
   - 本地密文配置层

### 1.4 主账本与内置库共享同一业务模型

当前已确认：

- 主账本与内置库共享约 `103` 张核心表
- 共享约 `130` 个字段
- 主账本里还能看到主键、索引、关系与设计器元对象痕迹

这说明：

- Rust 领域层不需要为“主账本”和“内置库”各建一套模型
- 更适合建立一套统一领域模型，再由不同 repository 适配不同数据源

### 1.5 共享参考库已经能读

`mhlink.mdb` 当前已成功只读打开，并确认至少有三类共享参考数据：

- `HBRate`
  - 利率规则
- `TBSecuPrice`
  - 行情价格
- `TBTransFee`
  - 交易费率

### 1.6 缓存层语义已经比较清楚

当前高可信结论：

- `MoneyHome8.cache`
  - 代码 + 中文名 + 拼音/缩写检索索引
- `Investment.cache`
  - 投资品分类字典
  - `_3`：交易型市场标的
  - `_4`：场外基金/公募基金
  - `_9`：货币基金/现金管理类产品

## 2. 已经足够稳定、可以直接指导实现的判断

### 2.1 `财务数据` 与 `记账` 不应合并

- `财务数据`
  - 更像浏览/管理中心
- `记账`
  - 更像录入/执行中心

### 2.2 预算/提醒/规划/目标应归同一工作区

从页面和窗体资源看，`财务分析` 更像：

- 财务预算
- 财务诊断
- 财务规划
- 财务目标

组成的专题中心，而不是报表页的附属模块。

### 2.3 参考数据应独立于主账本

利率、费率、行情都不应在 Rust 重构里写死。

至少需要独立的：

- `reference_store`
- `cache_store`

### 2.4 迁移路线不应以“旧库原位写回”起步

当前最稳妥路线仍然是：

- 旧数据可读
- 新数据可写
- 旧账本优先作为只读导入/兼容源

## 3. 仍未完全打通的关键问题

### 3.1 旧账本迁移映射

当前已知：

- 不带 `SystemDB`：无权限
- 带 `mh.mdw`：账号或口令无效

但尚未知道：

- 用户名是否固定
- 口令是否来自本地密文配置
- 是否存在运行时派生认证上下文

该问题只影响旧账本自动迁移深度，不再作为新系统功能分析、SQLite 设计和核心开发的主线阻塞。

### 3.2 主账本正式表结构

当前已有：

- 表名
- 字段名
- 索引名
- 中文语义线索

但还没有：

- 正式 `GetSchema`
- 正式 `SELECT`
- 主外键关系
- 样例数据

### 3.3 运行结果与视觉验证缺口

当前主要还缺：

- `记账` 动态菜单、页面跳转和真实写入结果
- 财务诊断、规划、目标的公式和代表性结果
- 报表精确 SQL、收益率公式、排序钻取、筛选边界、导出格式和打印结果
- 通用 XML 的完整导入语义、信用卡账单、备份压缩、附件目录和旧同步协议的真实格式与结果

补充：运行时 DFM 已确认静态控件、字段和事件，B15 完成了诊断、规划、目标、预算和计划提醒的代表性动态页面验证，B16 又逐页查询全部 `25` 张业务报表。B17 还确认了通用 XML 的导出结构、账户流水导入预览、交割单字段映射和标签筛选流程；这些不再是功能范围、页面内容或基本数据形态未知项。

## 4. 当前最推荐的 Rust 实现顺序

### Phase 1

- 先实现：
  - SQLite 账本创建和迁移
  - 账户、基础资料和通用交易仓储
  - 原子账户分录、余额与标签查询投影
  - 四大工作区壳层和命令状态
  - 旧账本 `legacy_import` 骨架

### Phase 2

- 再实现：
  - 收入、支出、转账和手续费写入闭环
  - 预算
  - 提醒
  - 报表骨架
  - 投资品检索
  - 记账入口及动态结果校准

### Phase 3

- 再补：
  - 证券/基金/外汇/理财/债权债务等主投资域
  - 财务规划 / 目标
  - 同步对象映射
  - 导入批次、交割单映射和附件服务骨架

### Phase 4

- 最后再补：
  - 导入导出
  - 备份还原、附件目录兼容和同步协议适配
  - 旧格式深兼容
  - 旧账本可能的直接写回

## 5. 当前阶段是否已经足够开始写代码

结论：

- `是，已经足够开始 Rust Phase 1 与 Phase 2 的正式编码`

原因：

- 功能面已经足够清楚
- 数据源边界已经足够清楚
- 领域模型已经足够清楚
- 工作区结构已经足够清楚

唯一不适合当前就承诺的，是：

- `100% 旧库兼容写回`
- `100% 页面细节完全复刻`

## 6. 当前最重要的阻塞

1. 诊断、规划、投资收益率和报表的精确计算口径
2. `记账` 动态交互与真实写入结果
3. 报表排序钻取、筛选边界、导出格式和打印结果
4. `test.mh8` 正式表结构和旧库迁移映射，仅作为并行兼容工作
5. 数据交换、备份、附件和旧同步的动态格式与结果校准
