# 交易与总账运行合同

本文把 B03 动态观察转换为 Rust 重构约束。旧 Delphi 窗体名只用于证据追溯，不作为 Rust 模块边界。

## 核心模型

### Transaction

`Transaction` 表达一个用户可识别的业务命令，至少包含稳定 ID、交易类型、业务日期、创建时间、状态、来源、备注和版本。交易头不直接承担余额计算，余额由分录和确定的排序规则推导。

交易修改不得静默覆盖历史。实现可以采用版本化修订或“冲销原交易 + 创建替代交易”，但必须保留原交易、替代交易和操作原因的可追溯关系。

### Entry

`Entry` 表达交易对账户或分类统计的影响，至少包含交易 ID、账户 ID、币种、定点金额、方向、排序和可选分类。一次已入账交易的全部分录必须在单个数据库事务内满足业务平衡规则。

转账至少包含转出和转入影响；手续费是显式费用分录，不能通过少记转入金额隐藏。跨币种转账还需要保存报价、方向、精度、舍入差异和使用日期。

### TransactionExtension

工资、报销、余额调整、充值、分拆和分期等专属字段通过有类型的扩展对象保存。不得建立一个包含大量可空字段的万能交易表，也不得通过窗体标题猜测交易语义。

## 单笔记账合同

日常收入和支出共享分类、金额、账户、标签、日期、备注和附件草稿。分类方向与交易方向必须一致，金额符号由领域规则统一处理，页面不得同时允许“支出 + 负数金额”形成双重反转。

2026-07-31 的两个独立真实保存会话进一步确认：同一 `TIncExpDlgFm + TIncExpEditFrame` 空白草稿初始标题为“日常收支”，选择收入分类“其它收入”后切换为“日常收入”，选择支出分类“教育培训”后切换为“日常支出”。两个方向都输入正金额；`Cash-CNY +3.00 CNY` 收入使余额 `608.00 -> 611.00`、CASH 分组 `9,495.70 -> 9,498.70`，`Cash-CNY -2.00 CNY` 支出使余额 `608.00 -> 606.00`、CASH 分组 `9,495.70 -> 9,493.70`，全局流水分别生成单边流入和单边流出，正常退出和冷启动后保持。目标模型必须持久化显式 `transaction_kind`，并在提交事务内校验分类稳定 ID 仍属于该方向；不能只根据标题或分类显示文字决定分录方向。

“保存并继续”每次只提交一个完整命令，成功后重置交易特有字段并按明确规则保留日期、账户或标签默认值。失败时保留当前草稿和错误定位，不得部分清空。

工资收入是独立复合交易，不能由普通收入加备注替代。`TPayrollIncomeDlgFm` 的 DFM 和当前类 19 个事件处理器确认三组可编辑事实：收入项目与金额、扣款项目与金额，以及选择社保人员后按社保账户维护的个人缴费和公司缴费。三张表都保存隐藏稳定 ID 并共用页脚汇总处理器，程序字符串明确包含“实收”，因此实收必须由组成确定性计算而不能独立覆盖。Rust 目标口径定义为 `实收现金 = 收入合计 - 普通扣款 - 个人社保缴费`，`社保账户权益增加 = 个人缴费 + 公司缴费`；公司缴费是单位福利，不进入收入账户现金。一次提交必须原子保存工资头、全部组成、实收账户流入、社保账户权益、标签、可选税务计算快照和审计事件。旧程序对个人/公司缴费的精确报表和净资产投影仍待真实保存校准，详见 `payroll-income-domain-contract.md`。

取款、充值和转账必须显式保存来源账户、目标账户、金额、手续费和日期。来源与目标相同、账户不可用、余额不足、币种不兼容和汇率缺失都应在提交前返回可定位错误。

第三方钱包充值和提现复用 `TRechargeDlgFm`，但必须由应用命令传入显式 `wallet_recharge` 或 `wallet_withdrawal` 模式。充值的本金方向为资金来源账户流出、钱包账户流入；提现的本金方向为钱包账户流出、资金去向账户流入。运行时 DFM 还确认两侧账户选择器均提供新建账户命令；Rust 版账户创建必须返回稳定账户 ID，成功或取消返回时都保留交易草稿。2026-07-31 的零手续费充值真实保存确认：`Cash-CNY -> 微信钱包` 本金 `2.00 CNY` 后，来源余额 `608.00 -> 606.00`、钱包余额 `2,986.44 -> 2,988.44`，全局财务记录显示流入/流出各 `2.00`；零手续费提现真实保存确认：`微信钱包 -> Cash-CNY` 本金 `1.00 CNY` 后，钱包余额 `2,986.44 -> 2,985.44`、资金账户余额 `608.00 -> 609.00`、CASH 分组增加 `1.00`，全局财务记录显示流入/流出各 `1.00`。两个方向净资产均不变且冷启动保持。充值和提现本金 `1.00 CNY`、手续费 `0.10 CNY` 的真实保存共同确认：资金发出侧总扣款为 `1.10`、接收侧只收到本金 `1.00`、全局投影为流入 `1.00`/流出 `1.10`、净资产减少 `0.10`。充值由资金来源账户承担费用，提现由钱包来源账户承担费用；领域模型必须把本金和手续费保存为可区分组成，允许来源账户流水合并展示总扣款，但费用报表、审计、修改和删除必须按组成准确重建。充值手续费修改进一步确认，费用 `0.10 -> 0.20` 只追加来源侧和净资产差额 `-0.10`，接收本金不重复记账；删除前必须显式确认，删除后本金与费用对账户、分组、净资产和记录列表的影响全部撤销，修改态和删除态均可冷启动重建。目标命令应使用稳定交易 ID、预期版本和幂等键，修改保存新旧值审计，删除采用可审计撤销或软删除语义；并发版本不匹配时拒绝覆盖。充值与提现的“保存并继续”都必须先原子提交当前草稿，再创建只保留钱包账户与日期的新草稿，对方账户、金额、手续费、标签、备注和附件不得泄漏到下一笔；两个方向的编辑关闭和删除否必须走显式零写入取消路径，确认删除必须完整撤销业务投影。两次打开关闭成功状态产生不同 Jet 文件哈希，兼容验收必须比较交易和投影而不是要求旧文件字节恒等。费用报表分类、提现费用修改差额、附件/标签/内联账户保留、余额不足和技术失败回滚仍不得标记为已兼容。

余额调整是现金、贵金属、期货、融资融券和保险等账户域共享的显式交易命令。编辑器读取 `account_id + currency_id + effective_date` 对应的账面余额和余额版本，用户只输入真实余额，领域层计算 `差额 = 真实余额 - 账面余额`。2026-07-31 的 `Cash-CNY` 样例确认，账面 `608.00`、真实 `609.00` 生成单条流入 `1.00`，账户、CASH 分组和净资产同步增加 `1.00`；修改同一记录为真实 `607.00` 后，原流入被替换为流出 `1.00`，账户和全局记录数不增加。修改页仍加载原始账面基线 `608.00`，因此调整事实必须保存或可重建基线、目标、差额和版本。编辑关闭与删除否零写入，确认删除完整恢复账户、分组、净资产和记录数；修改态与删除态均通过冷启动复核。默认类型的“保存并继续”先提交一个调整，再创建使用新余额版本的草稿：保留账户、日期和类型，账面余额刷新，真实余额、标签和备注清空。两个差额策略都允许零差额：默认策略生成零金额余额调整事件，日常收支生成零金额普通“对账收入”；零金额事实参与记录数、查询、审计、迁移和删除，但不改变余额及金额汇总。动态类型 `日常收支` 已确认不是调整事件的显示别名，而是原子转换策略：`delta < 0` 创建普通日常支出及稳定分类“对账支出”，其它情况创建普通日常收入及稳定分类“对账收入”；后续修改分别路由 `TIncExpDlgFm / 日常支出` 与 `TIncExpDlgFm / 日常收入`，金额为差额绝对值，不再加载原始账面/真实余额。日常收支“保存并继续”可以真实提交并保持编辑器打开，但旧界面会保留已提交的真实余额和备注，并继续显示陈旧账面余额；这是已证实的状态同步缺陷。Rust 下一草稿必须读取提交后的权威余额版本，保留账户、日期和策略，清空真实余额、标签、备注和附件。Rust 必须把默认调整事件和差额转普通收支建模为两个明确命令分支，转换事务不得同时留下重复调整事件。提交时必须校验同一余额版本；修改以稳定交易 ID 和预期版本替换同一事实，删除采用可审计撤销或软删除语义，禁止直接更新余额投影。对账收入/支出的完整报表口径、历史日期重算和系统对手分录仍待校准。旧 `TMHCalcuEdit` 可出现显示文本与内部数值失配，Rust 金额编辑器必须由单一强类型状态驱动。

## 分拆、报销与退款

分拆收支由一个交易头和多条分类分配组成。各分配金额之和必须等于交易总额；定点舍入产生的尾差应由明确规则处理，不能静默丢弃。

报销和退款必须引用原交易，保存已报销/已退款金额和剩余额度。部分报销、重复退款、超额退款和原交易已删除或已替代都需要显式校验。

退款、报销和冲销应通过关联交易反向影响余额和报表，不能直接修改原交易金额来抹去历史。

## 余额调整

余额调整是显式系统交易，用当前账面余额与目标余额计算差额，并使用受保护的系统分类或差异账户生成分录。它不能直接更新账户余额缓存。

调整前必须展示当前余额、目标余额、差额、日期和影响范围。删除或修改余额调整需要按普通交易修订规则处理，并触发后续余额重算。

## 批量记账与模板

模板是版本化的可复用草稿，保存名称、行定义和默认值，不拥有已生成交易。模板修改不应回写历史交易。

批量记账行至少包含日期、分类、账户、金额、标签和备注；批量转账行至少包含日期、转出账户、转入账户、金额、手续费、标签和备注。

旧程序明确跳过零金额行。Rust 版必须在提交前展示有效、跳过和错误行，并在结果中逐行报告。批次原子性应采用以下明确策略之一并在产品中固定：

1. 全部有效后整体提交，任一写入失败则整批回滚。
2. 用户显式选择“仅提交有效行”，返回每行独立结果和可重试标识。

不得在未提示的情况下静默部分提交。重复点击或网络/进程重试需要批次幂等键，避免重复生成交易。

## 分期合同

分期功能由 `InstallmentAgreement`、`InstallmentSchedule` 和实际入账交易组成。协议至少保存信用卡账户、分类、分期本金、总期数、首期日期、手续费或利息规则、每期金额、备注和状态。

生成计划时一次性创建完整期次，并明确哪些期次已经入账。编辑费率、期数或首期日期需要展示重算影响并保留旧版本；已入账期次不得被无痕覆盖。

分期入口至少受交易方向和账户类型约束。提前结清、取消未入账期次、修改剩余期次和删除协议都必须考虑已入账交易和信用卡账单引用。

## 查询、查找与筛选

全局财务记录、账户流水和筛选结果使用统一 `TransactionQuery`：账户范围、日期范围、交易类型、分类、标签、关键字、金额范围、状态、排序和稳定分页游标。

逐项查找保存“字段 + 匹配值 + 当前结果游标”，用于定位下一条；条件筛选保存查询条件并返回结果集合。列表刷新、排序变化或数据版本变化时，旧查找游标应失效或重新定位，不能跳到不可预测记录。

金额范围必须校验上下界，日期和文本匹配规则需要显式定义。大数据量查询不得使用无限制全表加载或大偏移分页。

## 列表操作与审计

修改、删除、替换分类、改变类型、转为计划、退款、复制粘贴、附件操作和批量设置都通过独立命令服务执行。命令至少记录操作者、时间、目标交易版本、输入摘要和结果。

批量命令在执行前固定选择快照和每条交易版本。若执行期间目标已变化，应拒绝冲突项并返回明确结果，不能对当前可见行重新取样后继续。

同日记录排序只修改稳定展示顺序键，不修改业务日期或创建时间。复制和粘贴必须生成新交易 ID，并保存来源交易 ID；“粘贴到今天”只替换业务日期。

## 附件、标签与备注

附件使用独立文件对象和交易关系，保存内容哈希、文件名、媒体类型、大小、存储位置和生命周期状态。删除交易前必须处理附件引用；共享附件不得被错误物理删除。

标签使用稳定 ID 的多对多关系。常用备注只是录入辅助目录，不应把备注文本提升为不可变主数据；删除常用备注不能修改历史交易备注。

## 图表与汇总

月度收支柱状图、本月分类构成、列表底部汇总和账户余额必须读取相同查询口径。以下规则必须集中定义：

- 转账是否排除在收入支出之外；
- 报销、退款和冲销如何抵减；
- 跨币种交易按哪个日期和汇率折算；
- 隐藏或注销账户是否包含；
- 草稿、计划和未入账分期是否排除。

图表结果应携带查询参数、账簿数据版本和估值快照。下钻到交易列表时复用同一条件，避免图表金额与明细合计不一致。

## 本地持久化建议

SQLite 至少需要交易头、分录、交易修订关系、标签关系、附件关系、模板、模板行、分期协议、分期计划和审计事件。余额和图表可使用可重建投影或缓存，但不能成为唯一业务事实。

所有写命令使用数据库事务、外键和乐观版本。金额用整数最小单位，汇率和比例使用受控十进制定点表示。任何缓存更新失败都不得使交易事实处于已提交但无法重建的状态。

## 验证要求

Rust 实现进入兼容声明前，至少覆盖：

- 日常收入、支出、取款、充值和同币种/跨币种转账的有效、无效、取消和失败路径；
- 手续费、汇率、舍入差异和账户余额平衡；
- 分拆总额、部分报销、重复退款和余额调整；
- 批量模板零金额跳过、逐行错误、幂等重试和事务策略；
- 分期生成、重算、已入账期次保护和提前结清；
- 修改、删除、复制、退款、类型转换、转计划和批量命令审计；
- 查找游标、组合筛选、稳定分页和大数据量性能；
- 全局列表、账户流水、底部汇总和概况图表口径一致。
