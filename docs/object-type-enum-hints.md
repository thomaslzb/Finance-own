## 3. 当前推断

### 推断 A：类型枚举并不只面向账户中心

这些中文标签很可能同时服务于：

- 账户类型
- 交易对象类型
- 资产负债类别
- 报表分类口径

### 推断 B：某些对象在页面和数据库中的叫法可能不同

例如：

- 页面上我们看到 `开放式基金`
- 主账本片段里看到 `货币基金`
- 页面上看到 `重大资产`
- 片段里还有 `实物资产`、`物品`

这说明：

- 数据层枚举不一定和 UI 文案完全一一对应
- Rust 中应允许：
  - `code`
  - `display_name`
  - `group_name`
  三层表达

### 推断 C：基金/债券/理财之间存在更细的口径区分

从当前线索看，系统至少区分：

- 货币基金
- 国债
- 非上市债券
- 银行理财产品
- 集合理财

这说明：

- 不应把这些对象在领域层里粗暴地都合并成一个 `FixedIncomeLike`。
- 更好的方式是：
  - 先保留原始类型码/原始标签
  - 在上层提供归类视图

## 4. 对 Rust 重构的直接意义

### 4.1 类型系统设计

建议至少保留两层：

- 原始类型枚举：
  - `raw_kind_code`
  - `raw_kind_label`
- 归并后的逻辑类型：
  - `CashLike`
  - `ReceivableLike`
  - `DeferredExpenseLike`
  - `SecurityLike`
  - `FundLike`
  - `BondLike`
  - `MoneyProductLike`
  - `PreciousMetalLike`
  - `InsuranceLike`

### 4.2 UI 展示设计

- 工作区页面显示时优先使用 `display_name`
- 报表归组时使用 `group_name`
- 迁移旧数据时保留 `raw_kind_label`

## 5. 当前局限

- 还不能确认每个中文标签背后的正式代码值
- 还不能确认这些标签是账户枚举、交易枚举还是对象枚举
- 需要在主账本正式认证打通后，优先验证：
  - `TBObjectType`
  - `TBTransType`
  - `TBAcctType`
  - `TBSecuType`
