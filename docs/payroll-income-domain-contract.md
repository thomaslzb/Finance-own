# 工资收入领域合同

本文将 `TPayrollIncomeDlgFm` 的页面证据转换为 Rust 目标模型。旧窗体名只用于追溯，不作为模块边界。

## 领域事实

- `PayrollIncome`：工资业务身份、账簿、币种、业务日期、实收账户、可选人员、备注、标签、状态和版本。
- `PayrollIncomeComponent`：税前工资、奖金、补贴等收入分类与定点金额。
- `PayrollDeductionComponent`：个人所得税及其它普通扣款分类与定点金额。
- `PayrollSocialContribution`：社保账户、个人缴费和公司缴费。必须关联人员，不能根据账户名称推断人员。
- `PayrollTaxCalculation`：可选税制版本、输入快照、计算结果、舍入规则和确认时间；计算器预览不等于已提交税务事实。

分类、账户、人员和标签全部使用稳定 ID。显示名称允许修改，不能参与交易种类、资金方向或关联对象判断。

2026-08-01 的动态校准进一步确认这一边界：`Cash-CNY` 必须从账户候选列表完成对象绑定；仅向收入项目编辑器写入“职业工资”显示文字不会形成有效项目行，提交时仍提示“请选择收入项目”。Rust 选择器必须返回稳定 ID 和当前版本，不能把显示文字、标题或可访问性名称当成已选业务对象。

## 目标计算口径

所有金额使用同一原币最小单位并执行受检整数运算：

```text
gross_income = sum(income_components)
ordinary_deductions = sum(deduction_components)
personal_social = sum(social_contributions.personal_amount)
company_social = sum(social_contributions.company_amount)
net_cash = gross_income - ordinary_deductions - personal_social
social_account_credit = personal_social + company_social
```

`net_cash` 不得为负。公司社保缴费不进入收入账户现金，而是作为单位福利直接增加对应社保账户权益。该目标规则需要用旧程序真实社保样例做兼容对照，但不会阻止 Rust 数据结构先按可审计组成设计。

## 原子提交

一次工资确认必须在一个数据库事务中完成：

1. 校验账簿、币种、账户、人员、分类、标签和预期版本。
2. 保存工资交易头和全部收入、扣款、社保组成。
3. 生成实收账户现金流入和社保账户权益分录。
4. 保存可选税务计算快照、附件关系和审计事件。
5. 从同一提交版本刷新账户流水、财务记录、收支报表、社保账户、预算和净资产投影。

任何组成失败时整体回滚。不得先写实收收入，再异步补写扣款或社保；也不得只保存实收金额而丢失工资组成。

## 页面状态

- 币种改变后重新过滤收入账户、分类和社保账户候选；不兼容的既有选择必须明确标错，不能静默换绑。
- 社保人员改变后按人员稳定 ID 重载社保账户，保留仍有效的草稿行并明确提示被移除的行。旧页面已确认从 `<无>` 选择 `Lzb` 时条件展开社保账户、个人缴费和公司缴费三列表格；目标页面必须保持同等可发现性，但不得靠人员显示名加载关联。
- 页脚汇总是草稿派生值，不接受独立编辑。
- 保存并继续先原子提交当前工资，再创建明确的新草稿；字段保留策略须通过旧程序动态样例校准。
- 税务计算器取消不修改草稿；确认只回填可审计计算结果，不直接入账。

## 验收缺口

- MoneyHome8 已确认单笔收入金额 `10.00`、无有效扣款和社保明细时，收入合计与“实收”都即时为 `10.00`；普通扣款、个人缴费和公司缴费是否参与旧版“实收”页脚仍待绑定真实对象后校准。
- 公司缴费对社保资产、收入统计、净资产和税务报表的精确影响。
- 零金额、负数、重复分类、多币种、关闭账户和人员无社保账户时的旧版校验。
- 修改、删除、保存并继续、税务计算、报表、导出、并发和失败回滚。
